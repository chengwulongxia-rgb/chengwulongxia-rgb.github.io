同一批16道題，生成上限32,768 tokens時，原始Qwen3.5-0.8B答對0題，套用作者公開權重差分後答對11題，相近幅度的指定隨機對照則是2題。修改確實改變了結果，但作者版在8,192上限只答對2題。這篇用真實Colab L4的96筆輸出，拆開權重修改、生成預算與完成行為；沒有重新請Astra讀權重，也不拿效果重播冒充它理解大型模型的證據。

## 原文摘要

2026 年 11 月 2 日，Rikiya Takehi 等人發表 Weight-Space Programming 實驗，測試語言模型辨認、編寫與修改神經網路權重的能力。最吸睛的結果，是作者報告 Qwen3.5-0.8B 經過局部修改後，在 MATH-500 的平均正確率從 7.9% 升至 48.1%。但這不是只把 Qwen 的原始數字貼進對話框、靠 Astra 觀察權重就完成修復：該項實驗提供 Python 環境與前向測試工具，讓編修器反覆觀察、提出修改並比較結果。[1][3]

Matthew Honnibal 隔天提出的批評，重點是不同實驗的條件被放進同一個能力敘事：小網路的「原始數字、無工具」辨認，與大型語言模型的「Python、測試回饋、權重修改」，不是同一個設定。後者可能有工程價值，卻不能直接替前者證明可以擴展到大型模型。[2]

原作者自己也把 Qwen 的收益主要連到反覆生成的修復，並公開另一個模型改善有限的後續案例。這不是本篇才揭穿的問題；需要分辨的是，局部修改有效、找到修改的方法有效，以及模型讀懂原始權重，分別需要什麼證據。[1][6]

## 一、先看一題：答對了，卻還是寫了三萬個 tokens

MATH-500 的 `test/number_theory/459.json` 問地圖比例：圖上 3 英吋代表實際 10 英里，實際距離 53.25 英里，在圖上是多少英吋，答案以分數表示？原始英文題目與固定作答指令完整保存在 JSONL，模型沒有收到參考答案。

這是事後挑來解說的案例：按預先固定的題序，取 32,768-token 條件下第一個「原版錯、作者版對，而且作者版結束思考」的配對。它恰好是第一題，但不能用這一題代表全體。

原版用了整整 32,768 tokens，被長度上限截斷。尾端反覆懷疑題目措辭，把同一句話當成可能的筆誤，卻沒有正常結束。作者修改版則以 `stop` 結束，最後得到：

```text
\boxed{\frac{639}{40}}
```

這與資料集參考答案一致。但作者版也用了 **30,200 tokens**，不是乾淨俐落的一行解法。在 `</think>` 之後的回答中，僅「Wait, I need to check the reasoning again.」就出現 22 次。這是對保存文字的逐字計數，不是另一套迴圈判定器。

因此，`thinking_closed=True` 不表示停止所有反覆，`finish_reason=stop` 也不表示便宜或有效率。這一題支持的是：指定修改在較長預算內讓回答完成並答對。它沒有證明推理過程已經簡潔，更不能單憑一題解釋全部增益來自哪個內部機制。

## 二、先分開三件事：看懂、找到修改、修改有效

只看數字能否辨認網路的用途，是一種測試；使用程式與觀察回饋找到有用的修改，是另一種；固定一份已經找好的修改，確認它改變了輸出，則是第三種。本篇只親自執行第三種，原作者與批評者的討論作為前兩種的背景。

作者公開的方法說明中，Qwen 編修器可以讀取張量、操作持續存在的 Python 工作環境，並透過有額度的前向工具觀察模型。一次額度可對一批練習題生成答案，最多 512 筆；也可以進行另一種 teacher-forced 觀察。因此，「50 次前向額度」不能理解成只試過 50 道題，更不能理解成沒有測試回饋。[3]

禁止反向傳播、梯度下降或訓練迴圈，沒有消除試誤本身。編修器仍可提出候選、觀察失敗、調整再比較。公開日誌能讓我們讀這個過程，但完整編修 harness 並未隨資料一併釋出。本篇也沒有呼叫 Astra，不把重播最後一份差分冒充自主發現的重現。[3]

## 三、實際改動的是哪裡？先看一個真實數字

作者的最終 p50c 差分只涉及第 15 與第 19 層的 MLP `down_proj.weight`。每個矩陣形狀是 `1024 × 3584`，各選 64 欄修改。這裡的欄，是一個中間神經元寫回 hidden state 的權重向量；不是把 64 個詞的機率直接改掉。[3]

從公開 checkpoint 的真實位元組取出第一個修改位置，第 15 層的第 0 列、第 0 欄，數值由：

```text
0.0235595703125 → 0.06494140625
```

另一個位置，第 19 層的第 0 列、第 1 欄，則是：

```text
-0.177734375 → -0.03759765625
```

這些是本機從固定版 safetensors 位元組重建出的值，完整單步紀錄也隨結果保存。單一位置當然不能解釋整個行為變化，但它提醒我們：修改比例小，不等於每個被改到的數字都只移動了一點點。

作者以選中位置計算，共觸及 131,072 個權重；轉成實際評測使用的 BF16 後，與原始位元組不同的數量是 130,188。有些數值雖被操作過，最後卻捨入回原值。把「觸及」與「實際不同」分開，才能讓別人重建同一個模型。[3]

## 四、不是下載一份自稱修改版的模型，而是逐張量核對

本篇固定作者日誌、基底模型與資料集的 revision。重建時先核對兩個原始張量的 SHA-256，再套用稀疏位置與新的 BF16 值，最後核對修改後的 SHA-256。兩端都符合作者 manifest，才進入推論。

Notebook 中的核心操作是：

```python
bits = base.contiguous().view(torch.uint16).numpy().copy()
assert sha_bytes(bits.tobytes()) == t['base_sha256']
edited = sparse_rebuild(bits, z[f't{i}_idx'], z[f't{i}_val'])
assert sha_bytes(edited.tobytes()) == t['edited_sha256']
```

用 `uint16` 看的是 BF16 的原始位元，不是先轉成其他精度再猜測是否接近。NPZ 讀取則明設 `allow_pickle=False`。同一組原始與修改後雜湊，也已在 GPU 工作之前，透過公開 checkpoint 的兩個對應 byte ranges 與 NumPy，在 CPU 上獨立核對；不需要為了檢查這兩個張量，先下載與執行整個上游專案。

推論採公開模型的設定、只載入文字張量，並明設 vLLM 的 `language_model_only=True`。三組都走同一條載入路徑，避免把視覺處理或不同權重命名方式混成實驗變因。模型與取樣條件固定，修改後的張量雜湊也另外保存。

## 五、隨機對照不是隨便撒一點雜訊

只有原版與修改版，很難回答「換個方向動同一批位置，也會不會改善」。本篇增加一組固定 seed 的隨機對照：先計算作者公開 BF16 編輯相對原版的差值，在同一批 64 欄內，各自置換列方向，再加回基底。

它保留的是每欄差值在再次捨入之前的範數。加回基底並轉為 BF16 後，實際範數與改變位置的數量仍可能略有差異，所以不能只靠一句「norm matched」帶過。本篇把捨入前後的範數、誤差、改動欄位與張量雜湊都寫入紀錄。

例如第 15 層，作者差值的範數為 `1.7488876203545387`，隨機對照捨入後為 `1.7489061238231256`；第 19 層分別為 `1.398763191406424` 與 `1.398921825731764`。這些 CPU 重建紀錄說明幅度相近，但範數接近本身還不能回答模型效果。

本篇只用一個控制 seed，沒有看過成績後挑選最差的隨機方向。即使作者版優於這一組，也只能回答這個指定對照，不能估計所有隨機修改的成功機率。

## 六、16 題、六個條件，不是 96 道獨立題目

題目來自固定版 MATH-500。先把全部 500 題用 `random.Random(20261104)` 打亂，取前 16 題，保存原始資料 SHA-256 與題目順序；選題在推論前完成，不依答案或模型成績挑選。[5]

每題測三組權重，以及 8,192、32,768 兩種生成上限；每個條件只有一次生成。同一道題在各組使用配對的 seed，temperature、top-p、top-k 與 presence penalty 固定。思考模式保持開啟，不把較容易結束的另一種模式偷放進其中一組。

預定的 96 筆輸出是 16 題乘上六種條件，不能當成 96 道獨立問題。它也不同於作者完整 MATH-500、每題四次生成的評測；本篇完成的96筆，也不是原始 48.1% 的數值重現。[3]

兩種上限用來觀察預算門檻，而不是先把較長答案視為比較聰明。Qwen 的模型卡本來就警告，0.8B 在思考模式下較容易反覆生成、無法正常結束。這是來源已說明的已知條件，不是批評者或本篇才發現的漏洞。[4]

## 七、答對、結束思考與撞上長度上限，分開記帳

評分取最後一個完整、括號平衡的 `\boxed{}`，再交給固定版 math-verify 比較。沒有 box 就算錯；解析或比對失敗會留下診斷，不從分母刪掉。評分器先通過整數正反例、等價分數與最後答案覆寫等測試，再處理模型輸出。

這裡有個容易誤讀的細節：沿用作者式讀法，思考段裡的 box 也可能被評為答對。因此，我們另外計算 `thinking_closed`，確認輸出有沒有 `</think>`。一段未結束的思考碰巧包含正確 box，與正常完成回答，不是同一件事。

結果至少要一起看正確數、`finish_reason=length` 的數量、思考關閉數、box 出現數、輸出 token 數與重複診斷。碰到上限只證明答案被截斷，不能單靠這個欄位宣布它進入迴圈；4-gram 重複也只是診斷，不是人工標註的迴圈真值。

對每個 token 上限，再按題目配對比較：原版錯、修改版對，是一次 rescue；原版對、修改版錯，是一次 regression。這比只列兩個百分比更能看見修改救回了哪些題，也傷到了哪些題。

## 八、完整 96 筆：作者方向有效，長預算才顯出大部分收益

以下每列的分母都是同一組 **16 道題目**，每題一次生成；「答對」「結束思考」與「撞上限」是不同事件，不能相加。例如作者長上限的11/16，是16題中最後完整boxed答案正確的11題；原版的0/16只描述這16題，不代表所有數學題都不會。

### 生成上限 8,192 tokens

- 原模型：答對 **0/16**，結束思考0/16，撞上限16/16，平均輸出8,192 tokens。
- 作者修改版：答對 **2/16**，結束思考2/16，撞上限13/16，平均輸出7,558.75 tokens。
- 隨機對照：答對 **1/16**，結束思考1/16，撞上限15/16，平均輸出8,037.75 tokens。

### 生成上限 32,768 tokens

- 原模型：答對 **0/16**，結束思考0/16，撞上限16/16，平均輸出32,768 tokens。
- 作者修改版：答對 **11/16**，結束思考13/16，撞上限3/16，平均輸出19,057.5 tokens。
- 隨機對照：答對 **2/16**，結束思考2/16，撞上限14/16，平均輸出29,455.125 tokens。

![Qwen3.5 權重編輯96筆實測，三組權重與兩種token上限]({{ '/assets/images/2026-11-04/qwen-weight-edit-lab-results.png' | relative_url }})

圖由保存的96筆原始輸出重新評分產生，不重新呼叫模型。灰色是8,192上限，藍色是32,768上限；每根柱的分母都是16題，底圖是平均生成token數，不是GPU秒數或費用。

作者修改版在兩個上限下都比這個指定隨機對照多答對；但短上限只有2題，長上限才到11題。它不是改完就突然能在短輸出內解決全部問題：較長的生成空間是本次結果的重要條件。

我們又事後核對同題的token IDs：原版與作者版各16/16個長短上限配對，共享長度內的前綴完全一致。作者版因此多答對的9題，確實出現在原本8,192上限之後，不是另抽了一套早期回答；沒有原本答對、延長後反而答錯的題。

隨機對照則只有1/16個配對具有相同共享前綴。它的長上限是在另一部VM補跑，即使模型、套件版本、控制權重雜湊、prompt與seed相同，也沒有逐token重現；本篇尚未定位差異來源。因此，隨機對照的1/16到2/16，只能報為兩種條件的觀察，不能同樣解讀成一條既有軌跡單純延長。

## 九、改善已驗到，能力歸因還沒有

在這批題目上，作者版比原版多救回11題，原版原先答對的題數是零，所以也沒有原版對、作者版錯的regression。指定隨機方向只答對2題，不能用「只是隨便動一動」概括作者版的全部收益。

但這仍沒有把新增的數學能力，與原有解題路徑比較能完成，拆成兩個獨立的因果機制。整體完成行為的改變、第一題仍需30,200 tokens，以及短長上限的差別，都支持先把完成行為列為重要解釋，而不是直接替模型內部命名新能力。若要估計各機制的貢獻，還需要多個控制seed、更多未參與調整的題目，及不靠停止反覆就能改善的錯誤類型。

這個區分也不能被誤用成反面的過度結論：我們沒有證明「模型沒有理解」，更沒有用本次差分重播推翻原作者所有小網路實驗。這次根本沒有請Astra當編修器，能回答的是公開修改的效果，不是編修器腦中發生了什麼。

## 十、另一個模型，作者也沒有得到相同收益

原作者另以較少反覆生成的 Gemma 3 270M 做後續測試。在其 50 次額度條件下，MATH-500 的格式寬鬆分數由 6.8% 變成 7.0%；作者沒有把它包裝成已建立的能力增益。這不是本篇重跑的資料，也不能和 Qwen 的嚴格 boxed 評分直接相減。[6]

這個負結果的重要性，在於不能把「修復某個模型的特定失敗模式」直接外推成「能普遍提升任何模型」。本篇的16題結果也不能代替那份跨模型測試，兩者應各自保留。

## 十一、這次怎麼跑完：80 筆加 16 筆，而非抹掉中斷

實際硬體是Colab L4，模型BF16，Python3.13.16、vLLM0.25.0、Transformers5.17.0、Torch2.11.0+cu129與math-verify0.9.0。固定套件、資料、張量與選題的證據都隨程式庫保存。

過程包含環境與模型載入失敗、一輪估時後主動停止，以及正式輪因時限留下80筆。最後只補跑缺少的隨機對照長上限16筆，沒有改題、縮短生成上限，或重抽比較有利的控制方向。全部五輪、安裝、失敗與停止確認累計185.51分鐘，在分次追加的200分鐘內；每輪VM都已停止並讀回確認。

這不叫單次完整GPU Run all。公開資料保留80筆與16筆各自的原始壓縮檔、兩輪封存的原生Notebook與生命週期紀錄；合併檔只新增來源輪次，不改模型文字與token IDs。完整96筆條件、prompt、seed、差分與環境核對後，再以CPU重新評分，錯誤與逾時診斷為零。

[主要原生Notebook](https://github.com/chengwulongxia-rgb/deep-dive-code/blob/7985ff3476001e03428937193ee8d453648c9021/weight-space-programming-lab/weight_edit_colab.ipynb)預設是CPU重播：讀取已保存的真實輸出，核SHA-256、重評、畫圖，不下載模型、不使用GPU，也不需要HF token。這條路徑已在乾淨Jupyter kernel跑完10個原生code cells，零cell error，完整summary與獨立合併核驗一致；11個離線測試另檢查grader正反例、BF16、資料原樣保留與GPU生成cells不變性。這兩個驗收不能混稱為新的96次GPU推論。

```bash
git clone https://github.com/chengwulongxia-rgb/deep-dive-code.git
cd deep-dive-code/weight-space-programming-lab
uv sync --frozen --extra notebook --python 3.13
uv run python -B -m unittest test_notebook -v
uv run python verify_replay.py
```

若要新跑GPU，才把Notebook的`RUN_GPU`改為`True`，並另設已授權L4、kernel記憶體中的HF憑證與主機硬截止。Notebook本身不申請、不自動停止付費VM，這次的歷史預算也不是下次的自動授權。

## 城武觀點

把模型從卡住改到能交卷，是值得保留的工程結果；把這個結果直接兌換成「讀懂大型權重」，我不接受。關鍵不是替理解畫一道永遠過不了的門，而是不能讓一種測試替另一種命題付帳。公開差分讓外部能驗證修改有沒有效，這點應當肯定；但完整編修harness尚未釋出，外部能重播結果，不等於能在同條件下重做發現過程。誰掌握完整測試環境，誰就掌握較多解釋結果的資訊，讀者不能拿一個總分補平這個落差。這次11題與2題的差別，足以讓我支持繼續研究特定編修方向；若要再往「理解」跨一步，請把問題、回饋權限與可推翻的判準先分開，別讓讀者自行把實驗之間的空白補成能力。

*城武的未解檔案——能改好權重是一項結果，「讀懂」不是隨附贈品。*
