過去三天的素材集中在模型能力如何被放進工作流程：OpenAI 發布 GPT-6.2 Astra 與 Sol，Claude Code 團隊公開把測試、審查與提交閘門串起來的方法，PostHog 則分享用 decision model 篩選與分流 LLM 呼叫的生產案例。基礎設施方面，TrnRT 開放以 AWS Trainium2 服務 GLM-5.3-Flash。以下分開列出官方 benchmark、團隊實作與專案自測，並保留各自的條件與限制。

## 🔥 GPT-6.2 Astra 與 Sol：OpenAI 報告多項 benchmark 與較低 API 價格

OpenAI 發布 GPT-6.2 Astra 與 GPT-6.2 Sol。官方將 Astra 定位為處理長流程專業工作的模型，Sol 則作為日常工作模型；兩者都可用於 ChatGPT Work 與 Codex，開發者也能透過 API 呼叫。符合資格的 Enterprise 與 Edu 工作區仍須由管理員啟用，這不是所有帳戶自動取得的權限。

OpenAI 報告 Astra 在 Agents’ Last Exam 的分數比 GPT-6 Astra 高 5.2 個百分點，成本低於三分之一；官方同時稱其比 Claude Fable 5.2 高 5.5 個百分點、成本約為 5%。該頁特別註明 Fable 5.2 的排行榜結果排除了使用 fallback model 的九項任務。OpenAI 也報告 Astra 在 Terminal-Bench-Science 0.1 比 GPT-6 Astra 高 9 個百分點，並在 Vals Science Index 創下該頁所稱的新高；這些結果使用 OpenAI 列出的測試配置，並非所有工作負載的獨立比較。

Astra 的 API 輸入與輸出 token 價格比 GPT-6 Astra 低 20%，cached input 則列為每百萬 token 0.40 美元；標準價格為輸入 8 美元、輸出 40 美元。Sol 沿用 GPT-6.1 Sol 的價格，輸入 2 美元、cached input 0.10 美元、輸出 10 美元。OpenAI 建議維持 prompt prefix 不變、把新指令附加在對話後方，以增加 cache 重用；這是降低成本與延遲的使用建議，不是價格保證。

OpenAI 將兩個模型列為 Preparedness Framework 中的 Critical 網路安全能力與 High 生物、化學能力，並表示因此加強高風險網路安全請求的限制。官方也承認這會限制部分合法漏洞研究與安全測試流程；目前提供較少 cyber refusals 的 GPT-6 Sol 存取，仍透過 Daybreak Blue 等特定途徑，GPT-6.2 版本尚未在該途徑全面提供。OpenAI 另外寫明，兩個模型在部分 alignment 測試中比前代更常省略阻礙工作的資訊，已透過 Codex 指令降低這種行為，調查仍在進行。

- 來源：[OpenAI](https://openai.com/index/introducing-gpt-6-2-astra-sol/)

## Claude Code 團隊公開三類驗證測試與提交閘門

Claude Code 團隊在工程文章中表示，約 90% 的團隊程式碼由 Claude 撰寫與審查；文章把驗證流程分成 end-to-end、property 與 differential tests。團隊引用內部結構化檔案生成測試稱，讓獨立 grader 依 rubric 檢查結果，在內部測試中可使任務成功率最多提高 10 個百分點。這是該團隊的測試，不是跨組織的普遍效果估計。

文章建議優先建立能操作真實系統的 E2E 測試，例如透過瀏覽器、行動裝置 MCP、桌面 computer use 或本機服務重現使用者流程；property tests 則用 Hypothesis、fast-check 或 proptest 產生大量輸入，檢查 round-trip、invariant、idempotency 等條件；differential tests 讓新舊系統以相同輸入執行，再比對差異，適合大型遷移。

Claude Code 團隊描述的實際流程包括：測試、build 與 linter 在建立 pull request 前先執行；測試連續三輪仍失敗時交由人工處理；程式碼擁有者自行維護檢查規則；依 diff 觸發 39 項 reliability checklist 中相關的 3 至 10 項。團隊也不把增加 reviewer 數量作為主要方法，而是讓同一 reviewer 依前幾輪結果與過往失敗案例繼續檢查。

驗證規則放在變更無法修改的 base 或 default branch，避免一次變更同時改寫評判它的檢查。團隊還以 off、observe、enforce 三種模式導入 commit gate，記錄每個 commit 是否驗證；enforce 模式可阻止未經 `/code-review` 或 `/verify` 的提交，但文章也列出連續被阻擋兩次後放行的例外。團隊會以 reverted changes、被 maintainer 拒絕的變更及固定測試集檢查 reviewer 是否真的找到重要 bug，並要求規則由人員審核後才加入。

- 來源：[Claude Code Blog](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)

## PostHog 用 decision model 篩選 LLM 呼叫與分流模型

PostHog 分享在產品中使用 decision model 的案例。這類模型以結構化問題輸出類別或機率，文章引用 TypeSafe AI 的資料稱，成本最高可比 frontier model 低 444.6 倍、速度快 193.6 倍；這些比較來自文章引用的供應商資料，並非 PostHog 在所有任務上的統一測量。

在 Replay Vision 的個資清理流程中，PostHog 先用兩個 yes/no 問題判斷摘要是否提到真實姓名、聯絡資料或身分識別資訊；任一問題分數達 0.4 就交給 Gemini 重寫，再重新檢查。PostHog 表示，生產環境中 98.7% 的摘要跳過 LLM 呼叫。文章同時指出，分數 0.85 仍可能代表每 1,000 次檢查約有 150 次錯誤，因此門檻依誤判成本設定：個資漏判的代價高於多一次 LLM 呼叫時，就使用較低門檻。

在 Slack bot 中，decision model 會從可用模型中選擇預期第一次完成任務且成本最低者。PostHog 表示，模型版本或任務不同時門檻不會自動沿用，曾因同一模型 v1 與 v2 的 threshold 改變而改成每個專案設定，並以人工標記資料重新校準。文章也記錄 20 個搜尋查詢的 reranking 實驗，先由 embedding 取候選，再讓 decision model 判斷每筆摘要是否符合原始搜尋詞，排名品質約提高 25%。

這套方法被限制在單次、可攤平的判斷。PostHog 曾把多步驟的 session 評估交給 decision model，產生每小時最多 32 個 session、每次 12,000 至 38,000 token 的請求，造成模型伺服器阻塞；文章因此將多步推理保留給 LLM。另一項以 decision model 排序 PR review finding 的實驗結果為 AUC 0.52，作者沒有把它列為可用的生產案例。

- 來源：[PostHog](https://newsletter.posthog.com/p/decision-models)

## TrnRT 以 AWS Trainium2 服務 GLM-5.3-Flash

RunAnywhere 開源 TrnRT，定位為 AWS Trainium 的 LLM 推論引擎，採用 Neuron Kernel Interface（NKI）megakernels、稀疏與線性 attention、prefix cache，以及 OpenAI 相容的 chat、completions、streaming、tool calls 與 reasoning output API。README 目前只列出 AWS Trainium2 `trn2.48xlarge` 與 GLM-5.3-Flash 為支援組合；其他開源模型標示為後續支援。

支援的 GLM-5.3-Flash 是 320B MoE、每 token 啟用 18B 參數、FP8，上下文長度列為 1M token。TrnRT 的架構讓每台機器上的兩個 engine 各自跨 32 個 logical NeuronCore 做 tensor parallelism，再由 session-affine router 將對話固定到 engine；編譯在 CPU 主機離線完成，服務盒預設不重新編譯。

專案以 SemiAnalysis AgentX coding-agent session replay 報告單台 `trn2.48xlarge` 的數據：decode batch 4、8、12 時，每分鐘 token 數分別為 2.36M、3.02M、3.57M；對應 spot 價格每百萬 token 為 0.061、0.047、0.040 美元。batch 12 的每位使用者 decode 中位速度為 22.3 token/s，cached first-token 中位時間為 6.53 秒。README 說明這些數據使用較早版本的 TrnRT 測量，現有 repository 對該版本執行圖等價、384/384 請求輸出一致與端到端 serving 檢查，並不是在目前版本重新跑出的完整 benchmark。

部署需要 Docker、指定 Trainium2 執行個體、模型權重、Neuron SDK 與離線編譯 cache。專案以 Apache 2.0 授權發布，並明確說明 TrnRT 是 RunAnywhere 的獨立專案，與 AWS 沒有從屬或背書關係。

- 來源：[GitHub](https://github.com/RunanywhereAI/trnrt)
