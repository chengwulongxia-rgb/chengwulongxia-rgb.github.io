## 🔥 Gemini Omni 1.2 Flash：影片長度增至 15 秒，價格下調 30%

Google 於 11 月 5 日發布 Gemini Omni 1.2 Flash，模型可原生生成與編輯最長 15 秒的影片；上一版本的上限為 10 秒。官方列出的 API 價格為 720p 每秒 0.07 美元，較 Gemini Omni 1.1 下調 30%。模型可在 3 至 15 秒間以一秒為單位指定影片長度。

這次更新也加入多輪對話編輯，使用者可用後續指令修改片段，而不必重新生成整段影片。Google 說明的工作流是先以 360p 或 720p 草擬，再將選定作品升級到 1080p 或 4K；這是產品支援的流程描述，頁面沒有提供不同解析度、片長與編輯次數下的完整成本表。

Google 以人物、產品或風格圖片、最長三秒的動態片段與音訊提示作為參考輸入，宣稱 1.2 Flash 會在鏡頭轉換中維持臉部、服裝、包裝文字與品牌色彩。公告展示的是虛擬試穿與展示海報案例，未提供獨立測試集、失敗率或在不同素材條件下的穩定性統計。

Gemini Omni 1.2 Flash 已在 Gemini API 與 Google Cloud 一般供應，Google 也將相關能力放入 Google Vids 與 Gemini for business。可使用的產品、解析度、升級方式與實際費用仍取決於各服務的介面與方案，不能只用每秒 API 價格推算所有工作流成本。

- 來源：[Google Blog](https://blog.google/innovation-and-ai/technology/developers-tools/introducing-gemini-omni-1-2-flash/)

## OpenAI BioBasicsBench：GPT-6 Astra 在 100 項濕實驗任務取得 66.7% 平均分

OpenAI 於 11 月 6 日發布 BioBasicsBench，這是一套評估 AI agent 解讀日常濕實驗原始資料的基準，共有 100 項任務，涵蓋蛋白質實驗、影像與細胞分析、定量與 assay、核酸方法及分子克隆。輸入包括凝膠與 blot 圖片、顯微鏡影像、測序檔、儀器輸出、實驗紀錄與操作影片；部分任務同時使用多種資料。

OpenAI 表示，任務由科學家以自身實驗資料建立，每項任務搭配專家撰寫的評分規準，並經未參與撰寫的 Ligo 科學家、外部博士級濕實驗研究者與內部人員審查。評分採 rubric 的逐項給分，也會要求 agent 判斷證據不足的情況。這套資料建立與審查流程由 OpenAI 說明，頁面沒有公開完整任務資料供外部重做。

在 xhigh reasoning effort 設定下，OpenAI 報告 GPT-6 Astra 的平均得分為 66.7%，95% 信賴區間為 60.3% 至 73.1%；GPT-5.6 Sol 為 43.8%，信賴區間為 37.6% 至 50.0%。評估涵蓋七個模型、37 組模型與推理設定，每組在 100 項任務上各嘗試五次，共 18,500 筆結果。這裡的百分比是任務 rubric 的平均 credit，不是 100 項實驗都被正確完成的比例。

同一份結果也列出失敗案例。Astra 在一項 colony PCR 判讀中正確分辨影像中的條帶群組，卻把群組對應到錯誤的實驗意義，選出 4、6、7、8 號菌落，而參考答案為 5、9、10 號；另一項菌落計數任務中，模型漏標相鄰菌落、漏掉可見菌落並在空白培養基上加標記，與基準答案相比約多算 12%。OpenAI 因此把控制組判讀、影像細節與判斷證據是否足夠列為仍需改善的部分。

- 來源：[OpenAI](https://openai.com/index/measuring-how-ai-agents-handle-wet-lab-science)

## OpenAI 與 Hacktron 合作測試第三方服務連接的漏洞

OpenAI 於 11 月 6 日宣布與 Hacktron 合作，雙方工程師與資安研究員將選定高優先級區域共同測試，重點放在 OpenAI 系統與第三方服務的互動。OpenAI 表示會透過 Daybreak Red 擴大 Hacktron 取得 frontier models 的權限，但公告沒有列出具體模型、權限範圍、測試環境或合作期限。

OpenAI 對 Hacktron 的描述是：該團隊使用 AI agent 進行程式碼檢視、滲透測試與 red teaming，過去透過 OpenAI Security Bug Bounty 回報應用程式、雲端基礎設施與身分系統互動方式中的漏洞。這些是 OpenAI 對合作方背景與合作理由的說明，不是本次合作已發現漏洞數量或修補成效的報告。

公告把這次合作放在 OpenAI 本週公布的其他資安措施旁邊，包括與 Cathedral 研究員進行安全 sprint，以及提高 bug bounty 獎勵。外部研究者若要提交發現，仍須依 OpenAI Security Bug Bounty 頁面列出的系統範圍與提交流程辦理；公告沒有在本文公布新的公開測試結果。

這則消息能確認的是合作關係與測試方向，不能據此推導 OpenAI 第三方連接器已完成安全驗證，也不能把取得 Daybreak Red 的資格視為對所有研究者開放。誰能取得模型、可測試哪些服務，以及發現後如何公開或修補，仍由合作與 bounty 的範圍條款決定。

- 來源：[OpenAI](https://openai.com/index/partnering-with-hacktron)

## ChatGPT MCP 連接器疑似在後續工具呼叫中切換 OAuth client

OpenAI Developer Community 一則 11 月 5 日發布的貼文描述一個 ChatGPT Apps SDK 測試案例：同一帳戶啟用兩個指向相同 MCP server 的連接器後，第一次需要確認的工具呼叫經由連接器 A 執行，後續帶有一次性確認碼的呼叫卻經由連接器 B 發送，使用者在對話中沒有看到切換提示。

貼文作者設定兩個連接器各自使用不同 OAuth client，並在第一個連接器的 widget 中完成確認。伺服器端將確認碼綁定在連接器 A 的 OAuth client，因此後續由連接器 B 兌換時被拒絕。作者表示，該次記錄中的確認碼確實在 A 產生、在 B 嘗試使用，所有測試都失敗；這是社群使用者的重現描述，不是 OpenAI 已完成的產品事故調查。

貼文把連接器而非 MCP server URL 視為資料與授權邊界，理由是相同 URL 背後仍可能代表不同租戶、合作方或環境。作者擔心，在伺服器沒有把確認值與 OAuth client 綁定的情況下，連接器之間的靜默切換可能把一個 app 產生的資料帶給另一個 app。這段是貼文作者提出的安全風險分析，頁面沒有證明已有第三方資料因此外洩。

作者預期的行為是：後續呼叫應沿用啟動流程的同一連接器與 OAuth client。該討論串截至抓取時有五個貼文、約 5,100 次瀏覽，頁面沒有列出 OpenAI 的修復公告、影響範圍或正式回應；因此目前可報導的是一個具體測試案例與其授權邊界問題，不是 ChatGPT 連接器普遍會發生的結論。

- 來源：[OpenAI Developer Community](https://community.openai.com/t/security-follow-up-tool-call-silently-routed-to-a-different-connector/1413053)
