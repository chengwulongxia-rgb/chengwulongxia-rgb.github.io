過去三天的素材集中在 LLM 的實作成本與基礎設施條件：一個小型 JAX 專案把 DeepSeek V3 的部分架構拆成可讀程式碼，NVIDIA 則示範需要兩台 DGX Station 才能容納的 GLM-5.3 服務；同時，面向代理的瀏覽器把多個工作階段集中到單一介面，另一篇報導則追查 GPU 供應與融資交易的關係。以下分開列出專案實際提供的功能、測試條件與尚未由來源證明的部分。

---

## 🔥 DeepSeek V3 in 190 lines：純 JAX 實作部分架構並在 MacBook Air 訓練

GitHub 專案 `deepseek-v3-jax` 以 190 行非空、非註解的 `deepseek_v3.py`，實作 DeepSeek V3 技術報告中的部分架構。程式包含 Multi-head Latent Attention、解耦 RoPE、一個共享 expert 加上 16 個 routed experts 的 DeepSeekMoE、免 auxiliary loss 的 expert balancing，以及 multi-token prediction。專案沒有使用 Flax、Equinox 或 PyTorch，參數以 JAX array 的 plain dict 保存。

作者公開的一次訓練使用 MacBook Air M5、24 GB 記憶體、36.2 million 參數，其中每個 token 啟用 13.6 million 參數；資料集為 207 本書、2,170 萬個訓練 token，預設設定跑 12,000 steps、約 2.6 小時。作者記錄的驗證 loss 從 step 250 的 5.02 降至 3.51，中位速度約每秒 10,700 token。

這個專案明確把結果限定為架構示範，而非高能力語言模型；訓練文本主要是美國公版的偵探與犯罪小說，模型大小、資料集與訓練規模也不能直接對應完整 DeepSeek V3。README 另提醒，釋出的 checkpoint 是 Python pickle，載入不可信來源的檔案可能執行程式碼；重現預設流程需要 Apple Silicon Mac、Python 3.12 與約 120 MB 的資料下載，CPU 也可執行但速度較慢。

- 來源：[GitHub](https://github.com/Vaibhaav-Tiwari/deepseek-v3-jax)

## GLM-5.3 NVFP4：兩台 DGX Station 以 vLLM 提供單一 API

NVIDIA Technical Blog 示範以兩台搭載 GB300 GPU 的 DGX Station，透過 ConnectX-8 RDMA 與 vLLM 的 tensor parallelism，服務 `nvidia/GLM-5.3-NVFP4`。這個量化 MoE 模型共有 753 billion 參數、每個 token 啟用 40 billion；NVIDIA 列出的 checkpoint 約 464 GB，超過單張 GB300 約 252 GB 的 HBM3e，因此兩台機器各自保存完整 checkpoint，啟動服務時再把權重分割到兩張 GPU。

部署條件包括兩台執行 Linux 的 GB300 DGX Station、RDMA 連線、Docker、NVIDIA Container Toolkit、每台至少 464 GB 可用磁碟，以及 Hugging Face 帳戶與 gated dataset 的存取權。服務使用 TP=2、FP8 KV cache、prefix caching 和四個 multi-token prediction 草稿 token；兩台機器共同處理每個請求，由其中一台透過 OpenAI 相容 API 對外提供端點。任一台單獨運作都不能完成這個配置的推論。

NVIDIA 以 SPEED-Bench Coding 的 80 個對話測試並行效能。在 prefix caching 開啟、四個 MTP 草稿 token 與 FP8 KV cache 的設定下，並行數 1、8、16、32 的整體輸出吞吐分別為每秒 107.4、386.0、607.8、385.0 token；並行數 16 時平均請求延遲為 136.46 秒，並行數 32 時升至 453.54 秒。這是 NVIDIA 在指定硬體、模型、服務參數與資料集上的基準，不等於其他提示、硬體或負載的服務速度。

- 來源：[NVIDIA Technical Blog](https://developer.nvidia.com/blog/when-one-gpu-isnt-enough-serving-glm-5-3-across-two-nvidia-dgx-stations-with-vllm/)

## agweb：不搶焦點的 macOS coding-agent 瀏覽器

開源專案 `agweb` 提供一個以 WebKit 為基礎的 macOS 瀏覽器，讓多個 coding agent 從 shell 操作同一個視窗中的分頁。README 描述的介面包括分頁總覽、頁面 snapshot、click、填寫表單、文章文字擷取，以及顯示操作前後差異的回覆；登入、MFA 或 CAPTCHA 可透過 `ask` 將分頁交給使用者處理，而不是把憑證或驗證碼寫進 agent transcript。專案也提供 `--secret-cmd`，讓密碼由外部指令供應。

作者在五個閒置頁面的比較中記錄，agweb 使用約 590 MB 記憶體，headless Chrome 約 730 MB，Playwright Chrome 約 1.6 GB；這是專案作者在自身環境的測量，README 沒有列出完整版本、測量方法或跨硬體重現結果。專案支援多個 agent 同時工作，並會暫停閒置分頁；目前安裝需求是 macOS 26 或更新版本，也可使用 Xcode 26 從原始碼建置。

限制條件包括只使用 WebKit、不提供 Chrome DevTools Protocol，Chrome 專用網站可能運作不正常；靜態請求路由及部分網站的廣告阻擋能力也有限，README 建議這類情況改用 Playwright。這個專案因此不是通用瀏覽器自動化介面的替代品，而是把操作視窗、可見性與多工作階段管理集中到 macOS 應用程式中。

- 來源：[GitHub](https://github.com/paul-nameless/agweb)

## NVIDIA GPU 融資交易：TechSpot 引述 WSJ 報導追查 AI 需求來源

TechSpot 11 月 14 日引述《Wall Street Journal》對 NVIDIA 臨時執行長兼財務長 Colette Kress 的報導，稱 NVIDIA 在 2026 年中後期推動更多與雲端服務商及 AI 公司的融資交易，用以吸收 TSMC 晶圓供應並維持 GPU 價格。TechSpot 的文章將這些安排描述為 NVIDIA 支持客戶購買自家晶片的循環融資，並提到一項原本包含 2500 億美元資料中心 backstop 的 OpenAI 交易後來被放慢、縮減或暫停。

文章也寫到，Kress 曾對交易規模表示疑慮，NVIDIA 到 2026 年夏季開始擔心晶片訂購量過大；這些細節是 TechSpot 對 WSJ 報導的轉述，並非本文直接取得的完整 WSJ 原文。TechSpot 同時報導，部分 GeForce GPU 售價超過原始 MSRP 的 160%，但沒有在這篇文章中提供完整價格樣本、時間序列或因果分析。

因此目前可確認的是媒體對融資安排、供應與價格的報導，以及文章所引述的各方說法；這些材料本身不能證明 NVIDIA 已透過交易蓄意操縱市場，也不能單靠 GPU 價格推導出融資交易對消費者價格的個別貢獻。NVIDIA 對相關指控的完整回應與 WSJ 報導中的原始證據，未在 TechSpot 頁面完整呈現。

- 來源：[TechSpot](https://www.techspot.com/news/114558-nvidia-deliberately-kept-gpu-prices-high-through-circular.html)
