一台微控制器能否跑語言模型，常被問成「能不能聊天」。Low-Zi-Hong 的 ESP32s3-LLM-Cluster 值得看的地方，反而不是這個問題。它把一個模型的推論工作拆成可觀察的資料流：文字先被切成 token，向量跨過板子，逐層經過注意力與 MLP，再回到主節點。即使不把它當成日常可用的對話產品，這仍是一個把記憶體、通訊與算子分割攤到桌面上的實作標本。

## 原文摘要

GitHub 將此專案定位為在多塊 ESP32-S3 上執行的「分散式管線推論引擎」，使用 1.58-bit、也就是 BitNet 的語言模型量化方式；專案描述另寫為 0.4B 模型，並稱其採三元量化。README 的架構說明卻寫成「切片後的 0.5B LLM」在七個 ESP32-S3 節點上運行。兩個數字並不相同，因此本文只能如實標示為文件內的 0.4B 與 0.5B 落差，不能把它硬湊成已被確認的單一模型規格。

README 的分工採一主六從。主節點負責 BPE tokenizer 與 token embedding；圖中標示 embedding 以 INT4 儲於 Flash，約占 14MB。主節點把 hidden-state vector 經由高速 SPI daisy-chain 傳給第一個計算節點。後續節點接力處理 Transformer blocks：RMSNorm、1.58-bit attention 的 Q、K、V、O 投影與 RoPE、放在 PSRAM 的 KV cache，以及 1.58-bit MLP 的 gate、up、down 投影。README 的示意圖以第一個節點執行第 0 至 3 層、第六個節點執行第 20 至 23 層為例，最後再把資料傳回主節點。

這個設計的關鍵不是讓七塊板子同時搶同一個工作，而是將層依序排進管線。每一站接收前一站送來的隱藏狀態，完成自己被分配的 attention 與 MLP，再交棒給下一站。因而，SPI 不只是接線方式，而是推論狀態的生命線；每個節點可容納多少權重與 KV cache、每次傳遞多少資料、任一節點何時等待，都是系統行為的一部分。

也正因如此，README 目前提供的是架構與分工說明，而非完整的效能保證。它沒有在所引用的內容中給出可比較的 token 速率、端到端延遲、功耗、錯誤率或長上下文穩定性，也沒有把此系統定義成可取代電腦的聊天服務。把「七節點」直接翻譯成「七倍快」，或把低位元量化直接翻譯成成熟產品，都超出了這份文件能支持的範圍。

從實作閱讀的角度看，這份 README 把通常混在單一執行檔裡的問題拆成幾條明確邊界。tokenizer 與 embedding 留在主節點，意味著輸入文字如何變成第一個向量，和後續層運算是兩段不同責任；計算節點以 Transformer block 為單位切片，意味著模型切分不是抽象的「分散式」，而是具體選擇哪些權重、暫存與中間結果留在哪一塊板子；daisy-chain 則使每一次跨板傳輸都成為系統的同步點。這些分界讓人能追查：若記憶體不足，問題在 embedding、權重或 KV cache？若結果晚到，瓶頸在某段層運算還是 SPI 交接？文件沒有替這些問題提供測量結果，卻清楚指出了應該量哪裡。

BitNet 的 1.58-bit 與三元量化在此也應被讀成部署條件，而非神奇宣言。低位元權重能否與特定的 Flash、PSRAM、向量傳輸格式及算子實作配合，才決定這種切片是否成立。README 圖中仍保留 FP32 hidden state，並列出 FP16 scaled to FP32 的 RMSNorm；因此不能只從「1.58-bit」推論整條資料路徑都以同樣精度或同樣成本運作。這正是嵌入式推論最有教育性的部分：模型名稱、權重量化、活化值、快取與通訊格式必須分開看，否則量化這個標籤很容易遮蔽真正的資源帳。

## 城武觀點

這類作品的價值，不在於替廉價 MCU 宣告一次對電腦的勝利，而在於把平常被 GPU 吞掉的代價攤開：權重放哪裡、KV cache 何時膨脹、層切在哪裡、傳輸如何卡住。商業推論服務把這些決策藏在雲端，使用者只看見回覆；這個集群反而讓執行、記憶體與分割策略變成可質疑的物件。真正受益的是想理解限制從何而來的人，不是等待一台 ESP32-S3 取代工作站的人。

*城武的未解檔案——把模型縮小不等於把限制消失；限制只是沿著 SPI，換了一種更看得見的形狀。*
